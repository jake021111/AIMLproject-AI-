0. 이번 작업의 계기
----------------------------------------------------------
프론트(Flutter) 개발자가 "앱에서 테스트할 .tflite 파일이 있는지,
클래스 순서/입출력 형식/테스트 이미지를 받을 수 있는지" 문의.
저장소에 .tflite 가 전혀 없는 상태였으므로,
(a) 프론트가 모델 완성까지 기다리지 않게 만드는 것과
(b) 실제 학습을 착수하는 것을 함께 진행했다.

3. 학습 환경 구축
----------------------------------------------------------

venv 를 둘로 분리했다 (요구 환경이 서로 다름).
  .venv-train   Python 3.12 + torch 2.6.0+cu124 + ultralytics   (학습, GPU)
  .venv-export  Python 3.12 + tensorflow 2.21 + onnx2tf + tf_keras + ai-edge-litert (변환)

GPU: RTX 3050 Laptop, VRAM 4.29GB -> CUDA 정상 인식 확인

batch 크기 변경: 32 -> 8
  CLAUDE.md §7.3 의 batch=32 는 4GB VRAM 에서 640px 학습 시 OOM.
  train.py 기본값과 CLAUDE.md 를 함께 8로 수정하고 근거를 주석에 남겼다.

학습 출력 경로 수정
  project 가 상대경로면 ultralytics 가 runs/detect/runs/<name> 으로 중첩시켜
  README·validate.py 의 경로와 어긋났다. 절대경로로 변경.

5. TFLite 변환에서 발견한 함정 (중요 — 전부 실측 확인)
----------------------------------------------------------
[1] Ultralytics 의 TFLite/LiteRT export 는 Windows 에서 동작하지 않는다.
    exporter.py: assert MACOS or (LINUX and not ARM64)
    -> ONNX 까지만 Ultralytics 로 뽑고 onnx2tf 로 잇는 경로를 만들었다.
       export.py 가 Windows 를 자동 감지해 ONNX 모드로 동작한다.
    참고: CLAUDE.md §15.4 의 "한 줄 export" 는 Linux/macOS 전제였다.

[2] 경로에 한글이 있으면 변환이 실패한다.
    ai_edge_litert / TF 의 C++ 레이어가 비ASCII 경로 파일을 못 연다.
    이 프로젝트 경로(...\졸푸바오\ai)가 해당.
    에러: Could not open '...\??Ǫ?ٿ?\..._float32.tflite'
    -> 변환 스크립트가 ASCII 임시 디렉터리에서 작업하고 결과만 회수하도록 처리.

[3] onnx2tf 의 -oiqt 직접 양자화 산출물은 실행되지 않는다.
    생성된 INT8 tflite 6종 중 INT8 계열 전부가 로드 시 거부:
      output->params.scale == 1. / 256 was not true. (LOGISTIC) failed to prepare
    TFLite 커널이 sigmoid 의 INT8 출력 scale 을 정확히 1/256 으로 요구하는데
    캘리브레이션 값이 미세하게 다르다.
    -> onnx2tf 는 SavedModel 까지만 만들고, 양자화는 TensorFlow 자체 컨버터
       (representative_dataset)로 수행. TF 컨버터는 sigmoid 를 1/256 으로 특수 처리한다.

[4] bbox 는 0~1 로 정규화해서 내보내야 한다.
    Ultralytics raw 출력은 bbox 가 letterbox 640 "픽셀"(0~640), 클래스 점수는 0~1 인데
    둘이 [1, 4+nc, 8400] 한 텐서에 섞여 있다. TFLite INT8 은 per-tensor 양자화라
    scale 이 640 쪽에 맞춰진다(실측 2.505).
    -> scripts/yolo_onnx.py 가 ONNX 내보내기 시점에 bbox 를 imgsz 로 나눈다.
       (torch.onnx.export 결과는 onnxslim 으로 단순화해야 onnx2tf 가 받는다.
        안 하면 Reshape 추론 실패: "Cannot reshape a tensor with 409600 elements".)

[5] full-integer INT8(가중치+활성 모두 INT8)은 이 Windows 경로에서 쓸 수 없다.
    TF 컨버터로 만든 INT8 은 로드·실행은 되지만 출력이 무너진다:
      bbox 4행 전부 0, 클래스 점수 최대 0.30 -> 0.16
    같은 ONNX 의 FP32/FP16 은 정상이다 (bbox 0.0042~1.0014, 점수 0.3040).
    따라서 정규화 위치 문제가 아니라 INT8 양자화 단계 자체의 문제다.
    YOLOv8 의 bbox 브랜치(DFL: softmax + matmul)가 per-tensor INT8 에 취약한 것으로 보인다.

    시도한 조합 (전부 동일하게 실패):
      정규화를 TF 래퍼에서  + 입출력 int8
      정규화를 TF 래퍼에서  + 입출력 float32
      정규화를 ONNX 단계에서 + 입출력 int8
      (대조군) 같은 ONNX 의 FP32 / FP16 -> 둘 다 정상

    추가로 시도한 것:
      onnx2tf -oiqt (flatbuffer_direct)      -> 로드 자체가 거부됨 (LOGISTIC assert)
      onnx2tf -oiqt -tb tf_converter         -> 로드는 되나 동일하게 무너짐
      supported_ops 를 풀어 float fallback   -> 동일

    -> **해결: dynamic range 양자화(가중치 INT8 / 활성 float)가 정상 동작한다.**
       크기 3.2MB 로 full-integer 와 사실상 동일하고, 출력도 정상이다.
       CLAUDE.md §7.4 가 이미 "Hybrid Quantization(weight INT8)" 을 규정해 둔 경로다.
       onnx_to_tflite.py 의 --quant int8_hybrid 가 이것이며 기본값이다.

    -> NNAPI 가속이 필요한 full-integer 는 Linux 컨테이너에서 재시도 중.
       ultralytics/ultralytics:latest-cpu 공식 이미지는 torch 가 깨져 있어 못 쓴다
       (AttributeError: '_OpNamespace' 'aten' object has no attribute 'cholesky').
       docker/Dockerfile.export 로 Python 3.11 기반 이미지를 직접 만든다.


6. 검증 도구
----------------------------------------------------------
scripts/verify_tflite.py 가 앱이 할 일을 파이썬으로 그대로 재현한다.
  텐서 shape/dtype/양자화 파라미터 출력 -> 문서와 대조
  클래스 점수가 0~1 범위인지 (dequantize 검증)
  bbox 가 0~1 범위인지 (정규화 검증)
  최종 탐지 결과 + 시각화 저장

float16 변환본 검증 결과 (정상 확인, 이것을 채택)
  입력  [1,640,640,3] float32
  출력  [1,84,8400] float32
  bbox 범위 0.0042 ~ 1.0011   <- 정규화 정상
  클래스 점수 0 ~ 0.3040
  conf 0.15 로 낮춰 시각화한 결과, 실제 벤치 위치에 bench 박스가 정확히 잡힘
  -> letterbox 역변환 / 전치 디코드 / NMS 전 구간 정상 동작 확인
     (pillar 를 cup 으로 잡는 건 COCO 에 기둥 클래스가 없어서 생긴 오분류로, 정상)
